# Nora SQLite POC — Isolated Benchmark & Feasibility Harness

**This is NOT part of the Nora application.** It is a disposable, isolated experiment that
answers one question with measurements: *should Nora migrate from PGlite to SQLite?*

Verdict and full analysis: **[RESULTS.md](./RESULTS.md)** — decision: **MIGRATE TO SQLITE**.
Companion documents: [migration-surface.md](./migration-surface.md) (per-file migration map),
[search-comparison.md](./search-comparison.md) (pg_trgm vs FTS5-trigram semantics),
[benchmark-results.json](./benchmark-results.json) (raw numbers, 14 suites).

Nothing outside `sqlite-poc/` was modified. No production code, schema, or database was touched.

## What's in the box

```
sqlite-poc/
├── src/
│   ├── schema/sqlite-ddl.mjs     # SQLite mirror of Nora's core schema (+ FTS5 trigram DDL, triggers, PRAGMAs)
│   ├── schema/pglite-ddl.mjs     # PGlite mirror with Nora's real PG types (citext, gin_trgm, identity, enums)
│   ├── engines/sqlite-engine.mjs # node:sqlite wrapper + drizzle-orm via sqlite-proxy adapter
│   ├── engines/pglite-engine.mjs # PGlite wrapper (extensions loaded exactly like src/main/db/db.ts)
│   ├── gen/generator.mjs         # deterministic synthetic library generator (1.3k/10k/50k/100k)
│   ├── ingest.mjs                # bulk loader (identical logical data into both engines)
│   ├── populate.mjs              # builds disk-backed populated DBs used by the benches
│   └── bench/                    # one standalone script per phase (b0..b13)
├── results/                      # raw per-suite JSON results
└── benchmark-results.json        # rollup (generated by src/rollup.mjs)
```

## Environment

- **Intel Core i5-10210U @ 1.60 GHz (4 cores / 8 threads), 7.8 GB RAM** — a low-power laptop;
  all numbers below were produced on this machine and are mutually comparable
- Windows 11 x64 (10.0.26200)
- Node 24.18.0 (`node:sqlite` — SQLite 3.53.1)
- Electron 41.7.2 (bundled Node 24.15.0 — SQLite 3.51.3), verified in the **real main process**
- drizzle-orm 0.45.2, @electric-sql/pglite 0.4.6 (from the repo's `node_modules`; run `npm ci` at the repo root first)

Each suite records its own environment block programmatically (`os.cpus()` / `os.totalmem()`)
into its result JSON at run time — treat those captured blocks as authoritative.

## Reproduce

```bash

npm ci

cd sqlite-poc

# 0. generate the synthetic datasets (deterministic, seeded; ~2-3 min for all four sizes)

# 1. build the populated disk-backed databases used by the benches (~1 min for 1.3k, ~1 min for 50k incl. PGlite)
node src/populate.mjs 1300 both

# 2. run the suites (each is standalone; ~seconds to a few minutes each)
node src/bench/b0-startup.mjs        # Phase 4: cold startup, 7 iterations/condition/size
node src/bench/b1-memory.mjs         # Phase 5: baseline vs SQLite vs PGlite commit-size checkpoints
node src/bench/b2-queries.mjs 50000 20   # Phase 6: 16 realistic query shapes
node src/bench/b3-search.mjs 50000 8     # Phase 6+7: search latency + semantic equivalence
node src/bench/b4-write.mjs          # Phase 8: insert matrix, FTS trigger cost, Nora-shaped ingestion
node src/bench/b5-savepoints.mjs     # Phase 9: HARD GATE - P1 savepoint scenarios (exits non-zero on failure)
node src/bench/b6-concurrency.mjs 50000  # Phase 10: WAL readers, read-during-write, writer contention
node src/bench/b7-crash.mjs          # Phase 11: SIGKILL mid-transaction, reopen, integrity
node src/bench/b8-shutdown.mjs       # Phase 12: close under read/write/straggler load
node src/bench/b9-smartplaylist.mjs 50000 # Phase 13: SmartPlaylistCompiler rule equivalence
node src/bench/b10-migration.mjs 50000    # Phase 15: real PGlite schema -> SQLite migration + verification
node src/bench/b11-forensics.mjs     # Phase 17: ported forensic invariants (exits non-zero on failure)
node src/bench/b12-orm.mjs           # drizzle-orm over node:sqlite (sqlite-proxy): equivalence + perf
node src/bench/b13-electron.mjs      # Phase 16: node:sqlite inside real Electron 41 main process

# --- post-review hardening round ---
node src/bench/b3b-search-hardened.mjs 50000 8  # search regressions CLOSED: norm-FTS + trigram-OR + JS pg-similarity scoring vs pg_trgm
node src/bench/b14-durability.mjs               # synchronous=NORMAL vs FULL throughput + 30-cycle SIGKILL corruption soak
# b15 needs the packaged build first (from the repo root):
#   npm run build && npx electron-builder --dir --publish=never
```

Smoke test (fast end-to-end sanity of both engines): `node src/smoke.mjs`

## Methodology notes (read before quoting numbers)

- **Fairness**: both engines run the same logical schema, the same generated dataset, and the
  same query shapes. PGlite is driven through the same API surface Nora uses
  (`PGlite.create` + extensions `citext`/`pg_trgm` + drizzle-orm/pglite).
- **Startup**: each iteration is a fresh OS process; both engines open a *cleanly closed*
  disk-backed DB (best case for PGlite — Nora's production churned-DB numbers are worse;
  see RESULTS.md footnote 1).
- **Memory**: commit charge (`PrivateMemorySize64` via PowerShell) + `process.memoryUsage()`,
  GC forced at checkpoints, 3 runs per condition, medians. Known noise source (~150 MB of
  GC-able drizzle module-init garbage, identical for both dialects) is documented in RESULTS.md.
- **Statistical hygiene**: 5-8 iterations minimum per condition (7 for startup, 200 for tiny
  lookups), median/min/max/p95 reported, no best-run cherry-picking; outliers kept in JSON.
- **Search semantics**: the PG side runs Nora's exact search SQL shape (ILIKE + regexp_replace +
  trigram `%` + `similarity()` ordering). Equivalence is measured as id-set overlap, not
  "FTS5 returned something".
- **No simulated anything**: no mocks, no fakes, no latency injection. Where a test kills a
  process, it really SIGKILLs it.

## SQLite configuration used (candidate production posture)

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;
PRAGMA temp_store = MEMORY;
PRAGMA cache_size = -16000;   -- 16 MB page cache
```
FTS5 external-content trigram tables over `*_ci` columns with sync triggers (cost measured in
b4; can be dropped + rebuilt for bulk imports).

## Drizzle story

drizzle-orm 0.45.2 (and 1.0.0-rc) ships **no** node:sqlite driver. The supported path is
`drizzle-orm/sqlite-proxy` with a ~40-line synchronous adapter (implemented in
`src/engines/sqlite-engine.mjs`). Verified: selects/joins/insert-returning/nested savepoints
produce identical results to drizzle-pglite (b12). drizzle emits exactly
`SAVEPOINT sp0` / `ROLLBACK TO sp0` / `RELEASE sp0` for nested transactions — the same SQL the
POC's savepoint gate (b5) proves correct.
